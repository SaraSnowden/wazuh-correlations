# Корреляции Kubernetes Audit для Wazuh

Четыре правила для разбора изменений доступа и сетевой изоляции в Kubernetes. Вход — одна JSON-запись Kubernetes Audit API v1 на строку. Правила используют встроенный JSON-декодер Wazuh. Для проверки достаточно менеджера, без подключения к кластеру Kubernetes.

| ID | Что должно произойти | Окно | Уровень |
|---|---|---:|---:|
| `110413` | После изменения `pods/ephemeralcontainers` открыт поток `pods/attach` к pod с тем же именем в том же namespace | 5 мин | 9 |
| `110423` | Именованный RoleBinding создан и вскоре удалён в том же namespace | 3 мин | 8 |
| `110432` | Один инициатор, кроме `system:node:*`, получил токены двух разных ServiceAccount внутри одного namespace | 90 с | 8 |
| `110442` | Один инициатор успешно удалил по именованной NetworkPolicy в двух разных namespace | 2 мин | 10 |

## Разбор сигнала

**110413 · Интерактивная диагностика.** Проверьте окно работ, образ временного контейнера и параметр `container` у attach-запроса. Правило связывает события по pod. Сессия могла открыться к другому контейнеру того же pod, а изменить конфигурацию мог другой оператор. Штатная диагностика обычно имеет заявку и владельца сервиса.

**110423 · Короткое окно доступа.** К моменту разбора RoleBinding уже может исчезнуть из текущего состояния кластера. Найдите запись создания, восстановите `subjects` и `roleRef` по истории конфигурации или сохранённому телу запроса, затем проверьте операции субъекта за этот интервал. Сверьте с системами временного доступа и заданиями CI. Сигнал подтверждает жизненный цикл привязки по имени, использование выданных прав требует отдельных событий.

**110432 · Несколько получателей токена.** Проверьте, обслуживает ли инициатор оба ServiceAccount по регламенту. Для брокера учётных данных такой запрос может быть штатным. Для настройки исключений используйте конкретного инициатора и namespace. Уровня аудита Metadata достаточно: содержимое токенов для разбора не требуется.

**110442 · Изменение изоляции нескольких приложений.** Сопоставьте удаления с планом вывода namespace из эксплуатации и журналом GitOps. Восстановите селекторы удалённых политик и проверьте оставшиеся политики для затронутых pod. Фактический эффект зависит от их совокупности. Массовое удаление через один запрос `deletecollection` находится вне покрытия.

## Подключение источника

Нужны исходные поля `apiVersion`, `kind`, `verb`, `user.username`, `requestURI`, `objectRef`, `stage` и `responseStatus.code`. Для attach сохраните стадию `ResponseStarted`, для остальных операций — `ResponseComplete`. Имена объектов должны присутствовать в `objectRef.name`. Уровень Metadata позволяет обойтись без содержимого запросов и ответов. Формат журнала и стадии описаны в [документации Kubernetes](https://kubernetes.io/docs/tasks/debug/debug-cluster/audit/).

Для файлового источника на агенте укажите фактический путь и формат `json`:

```xml
<localfile>
  <location>/var/log/kubernetes/audit.log</location>
  <log_format>json</log_format>
</localfile>
```

Каждый набор коррелируемых событий должен прийти через один Wazuh agent на один manager. Для двух кластеров используйте раздельные агенты-источники. При HA control plane сведите журналы API-серверов одного кластера в общий поток с сохранением порядка. Окна отсчитываются при обработке событий менеджером. Запоздалая доставка, перестановка или массовое воспроизведение архива меняют результат. Стандартные запросы с `dryRun=All` отфильтровываются. Семантика счётчиков описана в [справочнике Wazuh](https://documentation.wazuh.com/current/user-manual/ruleset/ruleset-xml-syntax/rules.html).

## Проверка на тестовом менеджере

На Wazuh Manager 4.14.10 прошли 17 сценариев: четыре с ожидаемой корреляцией и тринадцать контрольных. [Протокол прогона](tests/wazuh-4.14.10.txt) содержит ID итогового правила для каждой обработанной записи, у которой Wazuh вывел фазу сопоставления. Проверка использует синтетические события и не измеряет шум на реальном кластере.

На менеджере проверьте, что ID 110410–110442 и имя файла свободны. Из корня репозитория скопируйте XML в каталог локальных правил и проверьте конфигурацию:

```sh
sudo install -o root -g wazuh -m 0640 rules/kube_audit.xml /var/ossec/etc/rules/kube_audit.xml
sudo /var/ossec/bin/wazuh-analysisd -t
sudo python3 tests/replay.py
```

Каждый сценарий получает новую сессию `wazuh-logtest`. Внутри неё записи поступают последовательно. Раннер проверяет ID сработавших правил и завершает работу с ошибкой при расхождении. Один набор входных данных можно посмотреть отдельно:

```sh
python3 tests/replay.py --emit short-lived-binding
```

При проверке из рабочей копии с Docker скопируйте XML в тот же каталог менеджера внутри контейнера и вызовите `python3 tests/replay.py --container ИМЯ_КОНТЕЙНЕРА`. Для обработки живого потока после проверки перезапустите службу менеджера в согласованное окно. Для отката уберите файл набора из каталога правил, повторите проверку конфигурации и перезапуск.
